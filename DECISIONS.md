## 2026-09-23 — Fix: Tailwind producing zero output on the live deploy

- **Bug, not a scope gap:** the deployed site (`joinahuddle.netlify.app`) rendered as unstyled HTML — default browser buttons, no spacing/rounding/colors, plain stacked text. Root cause: `apps/web/app/globals.css` never had the `@tailwind base; @tailwind components; @tailwind utilities;` directives. PostCSS still ran the `tailwindcss` plugin every build, but with no `@tailwind` injection point in the source CSS it had nothing to expand into, so the compiled stylesheet contained only the ~15 lines of hand-written CSS (the `:root` color vars, `html/body` reset) and *zero* Tailwind utility classes — every `className="flex rounded-tile bg-s1 ..."` in the primitives was inert. This had been true since the Phase 0–1 scaffold; the `pnpm build` verification that session confirmed the build *compiled*, not that the CSS it produced was complete, so it didn't catch this.
- **Fix:** added the three `@tailwind` directives to the top of `globals.css`. Verified with the same sandbox font-stub workaround as prior entries: `pnpm build` now emits a ~16KB stylesheet containing real utility classes (`.rounded-tile`, `.grid-cols-2`, `.flex-col`, etc.), versus effectively empty before. Font stub reverted after verification, matching the earlier pattern.
- **Action needed:** push this commit and redeploy on Netlify (or trigger a new deploy from the dashboard) — the live site is still serving the unstyled build until that happens.

## 2026-09-23 — Real, database-backed rooms (mockRooms.ts retired)

- **`apps/web/lib/mockRooms.ts` is gone.** Rooms, joining, and participants now go through `@huddle/db` (Drizzle, `DATABASE_URL`) via new route handlers, so a room created on one device is a real row a friend's device can find and join — this is the thing the local-only mock explicitly could not do.
- **Hosting a room uses Supabase anonymous auth, not full sign-up.** `rooms.host_id` is `NOT NULL references users.id` by schema design (see Phase 0–1 entry) — no guest-host path exists in the data model, unlike participants/messages/picks which all support a `guestId` alternative. Rather than changing that schema, `apps/web/lib/supabaseClient.ts` calls `supabase.auth.signInAnonymously()` client-side (no email/password, just whatever name they typed) before creating a room; `POST /api/rooms` then upserts a lightweight `users` row keyed by that Supabase auth id. This matches what `users.authId` was already clearly meant for (comment in schema.ts: "mirrors the Supabase Auth user id"). **Requires Anonymous Sign-Ins to be turned on in Supabase** (Authentication → Sign In / Providers → Anonymous) — off by default. Not yet confirmed on; "Start a room" will fail with a visible error until Mo flips it.
- **Joining a room stays frictionless — no auth at all.** `POST /api/rooms/[code]` inserts a `guest_sessions` row (24h `expiresAt`) plus a `room_participants` row with `guestId` set, mirroring the existing guest pattern already used for messages/picks. A guest never touches Supabase Auth.
- **Ad hoc rooms (no specific game) get a throwaway `events` row** (`providerEventId: manual:<uuid>`, teams named "Watch Party") so `rooms.event_id NOT NULL` is satisfied without needing real feed data. A room started from Home's "Tonight" card instead carries the real ESPN game id/teams/time through as query params from `/` → `/create` → `POST /api/rooms`, which upserts a real `events` row keyed by that ESPN id (`events.provider_event_id` has a unique index, so the same game reused across rooms doesn't duplicate).
- **No Realtime yet** — the room screen (`/r/[code]`) polls `GET /api/rooms/[code]` every 4s via react-query instead of subscribing to live updates, so a friend joining shows up within a few seconds, not instantly. Video/audio/chat still aren't wired up (LiveKit), and the room screen still says so explicitly. Swapping polling for Supabase Realtime channels is a natural next step once that's worth the complexity.
- **"Leave" marks `room_participants.left_at`** via `POST /api/rooms/[code]/leave`, keeping the existing `room_participants_active_room_idx` (`WHERE left_at IS NULL`) meaningful — active-participant queries actually reflect who's still there.
- **Added dependencies to `apps/web`:** `@huddle/db` (workspace), `@supabase/supabase-js`, `drizzle-orm` (needs to be a direct dependency for pnpm's strict resolution, not just transitive via `@huddle/db`), `server-only`. `pnpm install` run and `pnpm-lock.yaml` updated locally — **Mo doesn't need to manually replicate the lockfile changes**; Netlify's build command is `pnpm install --no-frozen-lockfile && pnpm build` (`netlify.toml`), so it resolves fresh from `package.json` on every build regardless of the committed lockfile's exact state.

## 2026-09-24 — Real rooms debugged and confirmed live; Realtime replaces polling

- **Correction to the note above about the lockfile:** wrong. Netlify runs its own pre-build "Install dependencies" stage (`pnpm install`, `--frozen-lockfile` by default in CI) *before* `netlify.toml`'s `build.command` ever runs, so a stale committed `pnpm-lock.yaml` fails the build immediately regardless of what the build command says — `--no-frozen-lockfile` in `netlify.toml` never gets a chance to matter. Any time `apps/web/package.json` dependencies change, `pnpm-lock.yaml` must be regenerated and committed too.
- **`github.dev`'s drag-and-drop replaces folders, it doesn't merge them.** Dragging the delivered `apps` folder onto the existing `apps` folder in github.dev wholesale-replaced `apps/web`'s contents with only what was in the drag — silently deleting every file that hadn't changed (`layout.tsx`, `globals.css`, `fonts.ts`, `manifest.ts`, `providers.tsx`, `dev/states`, `tsconfig.json`, `next.config.mjs`, `postcss.config.mjs`, `tailwind.config.ts`, `public/icons/*`), which broke the build ("page.tsx doesn't have a root layout"). Recovered by diffing this sandbox's `git ls-files` against the live GitHub tree (`api.github.com/repos/.../git/trees/master?recursive=1`) to find every missing file. **Going forward: use plain github.com → "Add file" → "Upload files" instead of github.dev for multi-file deliveries** — confirmed twice now that it adds/replaces by filename without touching anything else, which is exactly the safety property github.dev's drag-and-drop doesn't have.
- **Root cause of "Could not create the room" once the build was fixed: a malformed `DATABASE_URL`.** The DB password contains `#` and `$`, neither percent-encoded (`#`→`%23`, `$`→`%24`) in the connection string, which corrupted how the URL parsed (Postgres client reported `ENOTFOUND postgres.fgyqhwizgpygftbjeygh` — the pooler *username*, misread as the entire host). Any Postgres password with special characters (`#$@:/?%` and space, at minimum) needs percent-encoding when placed in a `postgresql://` URL, or it fails in confusing, non-obvious ways. Fixed by rebuilding the full Transaction pooler string from Supabase's Connect panel with the password properly encoded, replacing the entire Netlify env var value (not just the password portion).
- **Confirmed live, end to end**, using a second browser tab as a stand-in for a friend's device: created a room, joined it by code from the second tab with a different name, saw both participants listed correctly, left cleanly from both sides.
- **Realtime replaces polling as the primary update path** (removing the gap flagged in yesterday's entry). Added `packages/db/migrations/0002_realtime_rooms.sql`: a public `SELECT` RLS policy on `rooms` and `room_participants` (required — Supabase Realtime's `postgres_changes` feature checks RLS before delivering an event to a client; against the prior deny-all it would silently deliver nothing, no error), plus adding both tables to the `supabase_realtime` publication. The public-read policy is intentionally as open as the app's existing access model: a room code is already the only access control, and `GET /api/rooms/[code]` already hands this same data to anyone with the code, unauthenticated — this policy doesn't expose anything new. Will need to become conditional once/if the unused `rooms.privacy` column becomes enforced.
- **`apps/web/app/r/[code]/page.tsx`** now subscribes to a `postgres_changes` channel filtered to `room_id=eq.<id>` on `room_participants` and invalidates the react-query cache on any insert/update/delete, instead of relying on a 4s poll. `refetchInterval` kept at a slow 20s as a safety net in case a Realtime subscription silently drops, not as the primary mechanism. `GET /api/rooms/[code]` now also returns the room's internal `id` (previously omitted) so the client has something to filter the subscription on.
- **Verified `pnpm build` clean in the sandbox** (same font-stub-then-restore workaround as always; ESPN's build-time schedule fetch still 403s here as expected, unrelated to this change).

## 2026-09-24 — LiveKit for real video/audio

- **Video and audio are real now**, not a static "camera off" placeholder. Mo created a LiveKit Cloud project and set `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` in Netlify (server-side only, no `NEXT_PUBLIC_` prefix needed — see below). Added `livekit-server-sdk` (token minting), `livekit-client` + `@livekit/components-react` (browser SDK and React hooks/components) to `apps/web`.
- **New route `apps/web/app/api/livekit/token/route.ts`** mints a LiveKit access token for `{ roomCode, participantId }`. `participantId` — already this app's de facto identity, passed via `?pid=` everywhere since the mockRooms days — doubles as the LiveKit participant identity, so there's one id per person per room rather than two parallel identity systems. Before minting, it checks the `room_participants` row named by `participantId` actually exists, is still active (`left_at IS NULL`), and belongs to the room named by `roomCode` — without that check, anyone could mint a token into any room's LiveKit session just by guessing a 6-character code. Returns `serverUrl` in the JSON response rather than requiring a `NEXT_PUBLIC_LIVEKIT_URL` env var, since Mo had already set `LIVEKIT_URL` without that prefix — avoided making him redo the env var setup for a naming convention.
- **New route `apps/web/app/api/rooms/[code]/state/route.ts`** — the only write path for `room_participants.mic_on`/`cam_on`. LiveKit has no idea this database exists, so when someone toggles their mic/camera, the room screen calls LiveKit directly (instant for that person) *and* POSTs here (a plain `UPDATE`, which Realtime — migration 0002 — already broadcasts to everyone else, same mechanism joins/leaves use). Two systems kept in sync by one call site, not by LiveKit and Postgres somehow agreeing on their own.
- **`apps/web/app/r/[code]/page.tsx`**: once `myParticipantId` is set, fetches a LiveKit token and wraps the participant grid in `<LiveKitRoom>` with `audio={false} video={false}` — nothing auto-publishes on connect, matching `mic_on`/`cam_on` defaulting to `false` at join. A new `LiveParticipantGrid` child component (must live inside `<LiveKitRoom>` for the hooks to work) uses `useTracks([Track.Source.Camera])` to get live camera tracks for everyone in the room, matches each to a DB participant by `identity === participant.id`, and renders it via `<VideoTrack>` into a new `videoElement` slot on `VideoTile` (see below). `<RoomAudioRenderer />` handles remote audio playback — no manual `<AudioTrack>` wiring needed. `useLocalParticipant()` backs two new toggle buttons (mic/camera) below the grid; the local tile shows LiveKit's own `isMicrophoneEnabled`/`isCameraEnabled` instantly rather than waiting on a DB round-trip, while every other tile still reflects `mic_on`/`cam_on` from the (now-live) DB row. Someone viewing the room without having joined (no `pid`) still sees the old static grid — no LiveKit connection is attempted for a non-participant.
- **`packages/ui/src/VideoTile.tsx`** gained one new optional prop, `videoElement?: React.ReactNode` — a live video element to render instead of the avatar when `camOn` is true. Deliberately generic (doc comment says so): this primitive doesn't know or care that the caller happens to be using LiveKit. Every other prop/behavior (joining spinner, poor-connection badge, reconnecting overlay, name pill, mic badge, spotlight sizing) is untouched.
- **API surface was read directly out of the installed package's `.d.ts` files** (`node_modules/.pnpm/@livekit+components-react@.../dist/hooks/*.d.ts` and `@livekit+components-core@.../dist/track-reference/*.d.ts`) rather than assumed from training knowledge, specifically to confirm: `useTracks` includes the *local* participant's own tracks (verified in `components-core`'s `getTrackReferences`, which builds its participant list as `[room.localParticipant, ...room.remoteParticipants.values()]`) — meaning one `useTracks` call covers everyone, local included, no separate local-track special-casing needed; and the exact `TrackReference` shape (`{ participant, publication, source }`, with `participant.identity` as the match key).
